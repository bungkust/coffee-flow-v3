# Taste Learnings
- Prefers a structured audit-first workflow: audit the app, write findings into a report file, get recommendations (what to implement, menus, settings, features), then implement, then verify end-to-end. Confidence: 0.85
- Wants audit results recorded in a report before any fixes are made, so issues are tracked and not lost. Confidence: 0.8
- Values maintained documentation files for consistency: agent.md for agent best practices and design.md to keep the design consistent. Confidence: 0.75
- Demands precision: all calculations and recipe data must be exact — audit every calculation in the app to make sure nothing is wrong. Confidence: 0.85
- After implementing, wants end-to-end flow checks (not just unit-level) to confirm everything works. Confidence: 0.85
- Prefers lean UI: if a bottom navbar has too many menus, recommends trimming it and moving entry points elsewhere. Confidence: 0.7
- Communicates in Indonesian (Bahasa Indonesia); respond in Indonesian unless they switch. Confidence: 0.8
- Cares about details like icon loading and menu/feature functionality being audited comprehensively, not spot-checked. Confidence: 0.7
- Wants terse "caveman" communication: drop articles, filler, and smooth words; use short words. Modes: `lite` (keep articles), `full` (drop articles), `ultra` (strip conjunctions). Stop via "stop caveman" or "normal mode." Confidence: 0.9
- Workflow preference: invoke relevant skill before any action — process/systematic skills first, then implementation. Never skip skill check even for "simple" tasks. Prioritizes brainstorming/systematic-debugging skills first. Confidence: 0.9
- Prefers rtk (Rust Token Killer) proxy CLI for concise shell output, verifies state via `bash scripts/check-status.sh --show`, and uses `rtk read`/`rtk grep`/`rtk test` directly instead of built-in file tools. Confidence: 0.85
- Scopes repo-wide audits to over-engineering and complexity ONLY; correctness, security, and performance bugs are explicitly out of scope for audit. Confidence: 0.85
- Prefers audit findings ranked biggest-cut-first, one-line-per-finding with tags (`delete:`/`stdlib:`/`native:`/`yagni:`/`shrink:`), ending with a `net: -<N> lines, -<M> deps possible` summary. Confidence: 0.8
- Prefers `pnpm` as package manager — runs tsc, unit tests, and e2e tests through `pnpm` (e.g. `pnpm tsc --noEmit`, `pnpm test`, `pnpm test:unit`, `pnpm test:e2e`). Confidence: 0.85
- Uses bounded, approval-gated refactoring: scopes work to one ownership boundary at a time, presents a design, asks for confirmation ("setuju?"), then implements — does not auto-execute across file boundaries without sign-off. Confidence: 0.85
- When refactoring, prefers merging semantically-similar single-purpose components into a universal component (e.g. Button + Chip → universal Button) rather than just deleting, with "best practice architecture" as the goal. Confidence: 0.8
- Updates audit docs (e.g. `docs/ponytail-audit-whole-repo.md`) after implementation to reflect merges in place of deletions. Confidence: 0.75
- Prefers comprehensive fix directives ('fix semua' = fix everything/all findings) rather than selective implementation of audit findings — wants all findings addressed, accepting the agent's practical scoping into bounded ownership boundaries during execution. Confidence: 0.85
- Extends the universal-component approach beyond Button+Chip: explicitly wants Dropdown, form fields (Input), and popups/overlays (Modal) each unified into a single universal component (e.g. Modal = "universal popup"), with Button as the universal interactive control. Confidence: 0.9
- Before removing any prop, interface, type, or method, greps the entire codebase for all callers/usages to verify 0 references — corrects earlier audit assumptions when usage is found (e.g. Input.active is actually used by PlaygroundPage; Modal.size is actually used by SettingsPage; removeDummyPantryItems/getAllMethods are actually used by PantryPage/Onboarding). Extends beyond props to interfaces/types (e.g. IRecipeRepository, SettingsService). Confidence: 0.88
- Uses a baseline proof for safe-refactor verification to show e2e failures are pre-existing, not regressions: git-stash-and-rerun the same failing specs and compare, or compare against Playwright's pre-session test-results/.last-run.json failure set (identical failing specs = pre-existing). Confidence: 0.88
- Parallelizes independent verification steps (tsc, eslint, dev-server startup) instead of running them sequentially. Confidence: 0.8
- Behavior-preserving cleanup: only removes code confirmed dead (0 callers); keeps primitives with distinct semantics (Badge, Card, Toast, ProgressBar) as separate components rather than forcing them into Dropdown/Modal, since merging them would be an a11y anti-pattern or cross incompatible lifecycles (transient vs blocking). Confidence: 0.8
- Refactors hand-rolled `getInstance()` singleton patterns to module-level instance exports (e.g. `export const dbService = new DatabaseService()`), treating the getInstance() pattern as an anti-pattern. Confidence: 0.85
- Groups multi-finding refactors into labeled batches (A1–A4, B1–B3, C1–C2) in a tracked todo list, running tsc + lint + e2e per batch before proceeding to the next. Confidence: 0.85
- When doing "fix all" directives, also fixes simple pre-existing lint errors encountered along the way (dead code, type casts, conditional hooks) — not only audit-specified items. Documents but leaves correctness refactors outside audit scope untouched. Confidence: 0.8
- When tsc/type-checking catches a wrongful deletion, uses `git restore <file>` to revert the entire file rather than manually re-adding the removed prop/method. Confidence: 0.8
- Removes single-implementation repository/service interfaces: when an interface has exactly one concrete implementation used solely as a type annotation, drops the interface and references the concrete class directly across the wiring (services, constructors, callers). Confidence: 0.8
- Prefers step-by-step, non-breaking execution: on "fix step by step without breaking" (stated twice in one session), applies one fix at a time and verifies each with `npx tsc --noEmit` → `npx vite build` → eslint before proceeding, rather than applying many changes at once; greps for dangling references before removing anything. Confidence: 0.8
- Prefers making a flagged-dead feature actually work over deleting it: when an audit classifies a setting/feature as unused (e.g. the Notifications toggle), wants it wired up and functional ("bikin jadi work") rather than removed — only genuinely dead code should be deleted. Confidence: 0.75
- Expects visual/layout consistency across pages and treats deviations as bugs: flags pages whose headers (padding/alignment) differ from the rest or sit flush against the edges, and reports them with annotated screenshots. Confidence: 0.8
- Treats content clipped/occluded by pinned bottom UI as a bug: expects every page to be fully scrollable to the bottom with nothing hidden behind fixed bars (SaveBar, FAB, bottom nav), and expects bottom padding to be sized against the actual fixed-overlay heights. Confidence: 0.7
- Live-tests the running app and reports each issue by pasting the exact local dev-server page URL (e.g. http://localhost:5174/recipes/new/edit?method=V60) together with the exact input data involved (e.g. the full recipe JSON payload), expecting the agent to locate and root-cause against that specific page. Confidence: 0.7
- Treats the user-supplied recipe data as the source of truth: when the preparation screen computes different values than the recipe states (e.g. shows a rescaled 69 ml pour / 66 g ice for a recipe that explicitly says 135 mL and 100 g ice, and rewrites the step text accordingly), reports it as a bug ("preparation tidak sesuai dengan resep yang di input") and expects the recipe's own numbers/instructions to be honored and passed through untouched, with app-derived heuristics only as fallback. Confidence: 0.7
- Uses a `/ponytail-review changes` slash-command review step on the current diff (surfacing over-engineering/shrink findings, tagged one-line-per-finding with a `net:` total) before applying them via a terse "fix". Confidence: 0.8
- Willing to skip flaky e2e tests ("test nya skip dulu") when failures are load/parallel-worker flakes and the change is already verified by tsc/lint/build, rather than chasing them. Confidence: 0.6
- Wants navigation consistency: top-level bottom-nav tab pages should have NO back button in their header (cites Pantry as the reference pattern) — back buttons only belong in drill-down/edit contexts (e.g. kept during BrewMethods "Select Equipment" edit mode as the cancel affordance). Requests these header changes "biar konsisten sama pantry." Confidence: 0.8
- On a reported bug, expects a codebase-wide sweep for the same class of defect, not just a fix at the reported site: says "make sure gak kejadian di tempat lain" and wants every other page/component with the same pattern audited and fixed. Confidence: 0.8
- Extends the minimal top-level-tab-page principle to floating action buttons: wants the floating "+" FAB removed from bottom-nav tab pages (e.g. Journal), keeping top-level tabs chrome-free for consistency. Confidence: 0.65
- Expects user-configured settings to be honored consistently across the whole UI: flags any screen that renders a value contradicting a chosen setting (e.g. a recipe page showing `oz` while the app unit is set to Metric) as a bug, framing it as "padahal metric udah di set" rather than a display nit. Confidence: 0.6
- Will repurpose the `/ponytail-audit` slash-command for a correctness/data-integrity sweep (not just its default complexity scope) when they argue real defects exist ("semua tempat make sure gak kejadian") — expects the sweep to cover every write/persistence path across the codebase, not merely the reported site. Confidence: 0.65
- After DB/repository/write-path changes, defines done as verified persistence for BOTH create and edit flows (create → full reload → still present; edit → reload → change persists) — "yang di create dan edit bisa ke save" — not just a code-level fix. Confidence: 0.7
- Prefers to run end-to-end/manual testing himself once the code is fixed: when browser verification tooling gets flaky, says "fix aja, biar aku test nya manual" and expects the agent to stop driving Playwright and just confirm tsc + eslint + build pass. Confidence: 0.7
- Prefers explicit user selection over automatic inference in the UI: when a value can be guessed but might be wrong (e.g. brewing method), wants the app to let the user just pick it ("suruh milih aja") via a visible picker rather than silently defaulting/overriding — and treats the absence of such a control as the real bug. Confidence: 0.6
- Values provenance/traceability of imported content: wants the original source (URL/reference) carried through the import flow — including inside the copied AI prompt — and persisted with the data so it can be revisited later ("biar bisa di liat lagi"). Confidence: 0.6
- Enforces UI consistency by naming an existing screen as the canonical reference and asking others to match it ("iconya pake sama kaya di jurnal", "biar konsisten sama pantry", "sama kaya journal"): when a visual element (icon/badge/avatar/text treatment) differs, wants it replaced with the same established component/treatment from the reference screen rather than a new/invented style. Confidence: 0.75
- Prefers long titles/text to wrap onto a second line (e.g. `line-clamp-2`) rather than being cut off with an ellipsis (`truncate`), asking other screens to match the Journal page — values showing full content over truncation. Confidence: 0.6
- Expects persisted source links to be actionable from the UI, not just stored: wants a recipe's source (YouTube/TikTok/web link) openable directly from the recipe detail page ("bisa di buka dari resep details"), implying a clickable/openable affordance rather than plain text. Confidence: 0.6
- Wants the screen kept awake for the whole time the user is on the active brewing screen (`/brew-flow`) — running, paused, or finished ("layar selalu on") — not only while the timer runs; re-acquires the lock when returning to the tab. Confidence: 0.6
- Expects automatic persistence at task completion, independent of the user's exit path: once a task finishes (e.g. a completed brew flow) it must be saved immediately, not only when the user taps an explicit "Finish & Log" button — navigating away (e.g. "Back to Homepage") must never lose the record ("harusnya langsung ke simpen kalo brew flow nya sudah selesai"). Confidence: 0.7
- Wants displayed/measured quantities to match what the user physically measures, not an aggregate: for iced recipes the total water must be split because the scale starts at 0 (ice already sits in the server) — the water gauge/target should track the actual poured amount (final step target) and show the ice separately ("total water harus di pisah, kalo ada ice gak bisa sama"). Confidence: 0.6
- Rejects UI values the app invents/fabricates rather than reads from the source: questions unexplained derived data ("pour and rest itu apa? gak ada di resep") and expects guessed/synthesized info (e.g. a fabricated pour/rest time split) to be hidden entirely when the source doesn't state it, not filled in with heuristics. Confidence: 0.6
- Wants each screen to keep a single, non-overlapping responsibility: content already handled on an earlier screen (e.g. water & ice preparation, dosing) must not reappear later — the brew flow should focus only on the pours ("brewflow fokus nuang aja"), with prep steps dropped before the flow and the prep screen keeping them. Confidence: 0.7
- Wants AI-generated/imported content to be strictly non-hallucinated: when the source (e.g. a YouTube video) omits data, the recipe generator must not invent or round numbers — extract only what the source states and use null/"" for anything missing ("biar gak halu generate resep nya"), ideally with a deterministic code-side guarantee, not just a prompt instruction. Confidence: 0.7
- Wants recipe titles to read naturally and be device/method-free: the name should describe the recipe without naming the brewer/dripper (stored separately) and without the word "Recipe" (e.g. "Immersion Ice Drip", "Tetsu Kasuya 4:6") — "gak usah sebut tools nya lagi". Confidence: 0.65
- Requires a computed value to render identically on every screen that displays it: after the brew-flow gauge was corrected to the pour total, the prep screen's "Total Water" badge still read hot+ice (235 vs expected 135) and was re-reported as "total water nya masih salah" — a value fixed on one screen but left inconsistent elsewhere counts as still broken, so fixes must be applied to all sites showing that value. Confidence: 0.6
- Expects derived aggregate totals to agree with the source's stated figures, and reports mismatches as bugs: questions the app showing ~4:30 total brew time when the video states 3:30–4:00, wanting the computed total to exclude preparation steps and land within the source's range. Confidence: 0.6
- When source data is missing, prefers a fallback derived from a documented domain best-practice formula over an arbitrary flat default: for unstated pour durations wants them computed from manual-brew flow rate (3–5 ml/s band, 4 ml/s sweet spot → `duration = round(pourVolume_ml / 4)`, matching 10 ml≈2.5 s, 30 ml≈7.5 s, 50 ml≈12.5 s, 100 ml≈25 s) rather than a blanket 30 s — supplying the exact formula/table himself ("pake rumus ini aja") and expecting it applied verbatim, only when the source stays silent. Confidence: 0.65
- Verifies mobile work on a real physical Android device, not just a green build: installs the APK and launches it himself, then reports runtime failures tersely (e.g. "udah behasil install tapi pas di launch, fatal error") and expects the real on-device logcat to be pulled to root-cause the crash. Confidence: 0.6
- Applies the review's shrink metric strictly and honestly: a suggested dedupe that would net-increase the diff (e.g. extracting a shared DEFAULT_BREW_FEEDBACK constant at ~+4 lines for a 2-line dedupe, needing a new home/file) is skipped even at the cost of a duplicated literal, with the arithmetic stated and an offer to add it if the user prefers a single source of truth — DRY is subordinate to a shorter diff. Confidence: 0.6
- Expects feature parity between the web browser and the native Capacitor Android build, using the browser as the known-good reference: reports native-only failures as bugs ("kenapa di device gak bisa save selection equipment, test di webrowser bisa") and expects the divergence root-caused — often traceable to environment-specific state such as a stale on-device SQLite schema. Confidence: 0.55
- Closes out mobile changes by asking to "bump version and reinstall": expects the Android `versionCode`/`versionName` bumped (e.g. 1 → 2, "1.0" → "1.0.1") and the rebuilt APK reinstalled and launched on the connected device, treating that as the default shipping step after a fix. Confidence: 0.55
- Treats SQLite schema migrations as append-only with strictly increasing, never-reused version numbers: after a reused migration version silently skipped on an existing device install (PRAGMA user_version already at that number, so "version > current" was false), adopts the rule of always taking the next unused version (e.g. 13, not a reused 12) rather than back-filling gaps. Confidence: 0.5
- Expects content parity across every brewing method: each tool should ship with built-in default recipes — settled on 3 per tool ("tiap tools 3 aja"), so an empty method list (e.g. Keurig, Hario Switch, Phin) is treated as a gap to fill rather than acceptable. Confidence: 0.6
- Extends provenance/no-hallucination to built-in seed content: seeded recipes must be researched from real references (web search/fetch) and carry a `source` citation for their numbers, rather than having ratios, temperatures or step times invented by the agent. Confidence: 0.75
- Requires shipped/built-in content to trace to a credible external source and will remove uncited content outright rather than keep it: asked to delete every recipe lacking a clear, credible source (web, YouTube, Instagram, TikTok, etc.) and keep only the sourced ones — "hapus resep2 yang gak punya source yang jelas dan credible". Confidence: 0.75
- Repairs legacy schema drift on upgraded installs with a data-preserving table rebuild: when an older install carries obsolete NOT NULL columns the current code no longer writes (e.g. `app_settings.updated_at`, `backups.status`) so every insert fails, adds a migration that creates the corrected table, copies the rows over, drops the old table and renames — keeping existing user data intact instead of just ALTERing columns. Confidence: 0.55
- For Android/Capacitor builds, pins the JDK explicitly (JAVA_HOME pointed at JDK 23) because the project targets Java 21 while the shell default is JDK 17, and stops the Gradle daemon (`./gradlew --stop`) after clearing caches so a stale daemon does not replay deleted paths. Confidence: 0.55
- Declares SQLite plugin options explicitly on Android instead of relying on defaults: sets `androidIsEncryption: false` in capacitor.config.ts because the plugin otherwise defaults encryption on and fails to initialise ("CapacitorSQLitePlugin: null") when it cannot build a Keystore master key. Confidence: 0.5
